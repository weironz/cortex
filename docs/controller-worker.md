# controller + worker：调度中心与执行体的架构定案

状态：**v2（2026-08-27，v1 经四路对抗评审后重写）**。
调研输入：仓库现状四路 + 业界四路（Claude Code / Agent SDK、OpenHands /
goose、编排框架与 durable execution、反向隧道选型），关键结论带出处。
对抗评审四路（信任与安全、离线与既有决策、失败模式与运维、过度设计）
判定 1 REVISE + 2 BLOCK + 1 REVISE；v2 吸收了全部致命与硬伤级发现，
**砍掉的比加上的多** —— 这正是评审的结论：骨架成立，血肉过剩。

---

## 一句话结论

**中心化「账本与中继」，去中心化「执行」；子 agent 的生命周期留在 worker
进程里；路由判据保持「谁此刻拿得出绑定」，不引入第二真相。**

原始提问是「能不能让 controller 统一管控子 agent 的生命周期与 agent 间
对话」。调研的回答是：**账本（会话历史、预算）该中心化，生命周期与消息
不该** —— 三家独立证据指向同一处：

| 谁 | 试过什么 | 结果 |
|---|---|---|
| OpenHands V0→V1 | 循环在云端 controller、沙箱只执行动作 | 「agent 与沙箱两个进程，一个崩另一个继续，会话损坏」；V1 把循环整个搬进 worker，生产系统性失败降 61%（[论文 2511.03690](https://arxiv.org/abs/2511.03690)） |
| AutoGen → MAF | 中心 broker 管 agent 注册、消息路由、生命周期 | 始终 experimental，微软在继任框架 MAF 1.0 里**没有携带它**，退回单进程组合（[迁移指南](https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-autogen/)） |
| Cognition (Devin) | 任意 spawn + agent 互发消息 | 「不可靠」；可靠的只有**单一 root agent 把隔离子任务派到独立沙箱，子 agent 之间从不交互**（[Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)） |

反方向也有实证：UC Berkeley MAST（1600+ trace、7 框架）里 **agent 间失调
占失败的 36.9%**（[arXiv 2503.13657](https://arxiv.org/html/2503.13657)）。
Claude Code 的 agent teams 是现存最接近「多 agent 产品化」的东西：
teammate 生命周期全在 lead 进程、消息走**本地 JSON mailbox 文件**、
跨机器时服务端**只中继纯文本**（[官方文档](https://code.claude.com/docs/en/agent-teams)）。
没有任何一家把子 agent 生命周期交给远端服务。

我们已经站在正确的一侧：循环在 `cortex-local`、账本在 `cortex-store`、
agentd 连 `cortex-agent` 都不依赖。这次架构不是转向，是**把已有的形状
说破、补齐一条传输（反向隧道）、并给将来的扩展写下触发判据**。

## 角色定案

```
            ┌──────────── controller（cortex-agentd）────────────┐
            │  账本：episodes / sync_log（已有）                  │
            │  名册：谁在线、够得到哪些会话（presence，已有）      │
            │  中继：客户端 ⇄ worker 字节透传（sandbox_proxy）    │
            │  预算：配额与并发上限 —— 只覆盖经它的流量           │
            └────┬───────────────────┬───────────────────────────┘
                 │ docker（托管）     │ 反向隧道（阶段 1 新增）
          ┌──────▼──────┐     ┌──────▼──────┐
          │ 容器 worker │     │ 桌面 worker │   ← 将来的远端 worker
          │ cortex-local│     │ cortex-local│      = 同一形状，见触发判据
          │ 循环+工具   │     │ 循环+工具   │
          │ 子agent     │     │ 子agent     │
          └─────────────┘     └─────────────┘
```

**controller 做的**：账本、名册、中继、预算（⚠️ 预算只覆盖**经它**的
流量 —— 桌面 UI 直连本机 worker、或用户自带 key 时，闸不在它手里，
界面与文档不许把它说成全局上限）。

**controller 永远不做的**：跑 agent 循环（`runner.rs` 的安全论证：它是
直接处理模型输出的进程）；管子 agent 生命周期；转发 agent 间自由对话。

**worker 做的**：agent 循环、工具、workspace、每会话 FIFO 队列、
**子 agent 的全部生命周期**（同进程、同沙箱、只读、限 4 个、
await 栈连坐取消 —— 今天怎样，以后还怎样）。

「托管」与「观测」的分界：**谁拉起进程，谁管生命周期。** controller
只对自己 `ensure` 出来的容器有生杀权；桌面 worker 的重启预算在壳子里，
重连由 worker 自己带预算做。

## 路由：判据不变，只换传输

**v1 在这里栽了跟头，值得写明白。** v1 提出 `pin_to_worker`：会话钉到
持久 worker id 上、路由查钉定。四路评审两路致命：

- 重装系统 / 换盘之后密钥对没了 → 新 id；而工作区文件与绑定从备份
  恢复回来了。钉定指着一个**永远不会再上线的 id**，会话永久不可达 ——
  而唯一救济（显式迁移）的第一步 `export_workspace` 要在**旧 worker**
  上执行，它已经不存在了。死锁，无逃生口。
- 现状代码恰好是对的：路由判据是「哪个在线 agent **此刻**报告持有
  绑定」，每 30 秒自我修正 —— 重装后新进程一个心跳周期内接管。
  `model.rs` 那条论证（「本机绑定天然只在那一台机器上，比 device id
  更硬 —— id 在重装/克隆之后会骗人」）说的正是这件事；v1 引用了它，
  然后把路由第一判据换成了一个 id。

**定案：路由判据保持「谁此刻拿得出绑定」。** 不引入 `pin_to_worker`、
不给会话记 worker id。「会话在哪台机器」的展示走 `machine_hint`
（名册里已有，明文注释「是提示不是身份」）。

**「不可达」的展示不需要任何新状态。** v1 说「做成可同步的派生状态、
不落库」—— 三路评审同时指出这自相矛盾：本仓库唯一的同步通道是
`sync_log`，不落库的东西走不了它。而事实是 **`GET /agents?session=`
已经存在**（per-machine 的 `has_session` + `attachable`），只是客户端
一行引用都没有 —— 病因是 UI 没接一个现成端点，不是状态不可查。
修法从「新造事件 + 派生状态（一个阶段）」缩成「接 UI（列进阶段 1
交付物）」。

**worker 掉线绝不悄悄换机重跑** —— 这条不变（文件系统身份论证）。
⚠️ 但它只约束**桌面/远端 worker**：云会话的容器被空闲回收后由
`ensure` 自动重建（卷保留、快照叠加恢复），那是既有生产行为，
不在此列。v1 的全称表述把这条现役路径也禁掉了，v2 收窄。

## 子 agent：生命周期不动，可观测降档补

现状：子 agent 是纯进程内 await 栈产物，事件被 drain（不上界面）。

**v1 说「事件全量进 `Run` 重放缓冲」，评审击穿了它**：缓冲的体量设计
建立在「相邻 Delta 合并 → 条数 ≈ 工具调用数」上；四路并行吐字要么
混流（drain 当初防的正是这个）、要么按 `subagent_id` 分列后相邻合并
失效，缓冲回到每轮上万条 —— attach 时在锁内 clone 它，整轮事件管道
停顿。

**定案：只进工具行级事件，delta 不进。** 每个子 agent 在界面上是
一行「子 agent N：任务摘要 · 状态」+ 完成后的结论折叠块 —— 与工具行
同一形状。`ChatEvent` 加 `subagent_id` 是 `cortex-proto` 的**线协议
变更**（v1 说「零新协议」不成立，是「零新通道」），三端渲染是真实
工作量，列进排期。

**约束 2 违例已修**（与本文同一批提交）：`subagent_spec` 曾向模型宣传
子 agent 能「检索资料库、联网搜」而目录里没有那两样 —— 描述已改为
只承诺真实能力，并有测试钉住「承诺 ⊆ 目录」。要给子 agent 联网，
先过 J2 那道口（web_search 把用户的话发到第三方），不是改一句话的事。

**跨 worker 的多 agent**：唯一被生产验证的形状是「root agent 把隔离
子任务派到别的 worker，零对话」（Cognition）。等真实用户要的那天 ——
在那之前它是「造好没人调用」。

## 反向隧道（阶段 1，用户已拍板）

**选型：worker 出站 WSS 长连到 controller + yamux 多路复用**
（[rust-yamux](https://github.com/libp2p/rust-yamux)：每流独立流控，
初始 256 KiB 窗口，慢流只堵自己 —— 评审专门攻过这条，攻不破）。
每轮 SSE 一条子流，心跳并入隧道。落选者一行带过：russh SSH-over-WS
多买的端到端加密在当前拓扑下买不到（见下）；rathole/frp/chisel 加密
终结在中继（伪 e2e）且嵌不进单二进制；WireGuard/libp2p 杀鸡用牛刀；
QUIC/WebTransport 未生产就绪。完整对比在调研档案。

**端到端加密显式推迟，并纠正立项时的一句话。** 立项 roadmap 写过
「顺手把中继明文解决掉」——**不成立**，2026-08-25 的归档决定是对的：
agentd 存着全部 episodes、也是它在调 LLM，**它本来就是内容持有方**，
在它面前加密隧道买不到任何东西。真 e2e 的试金石：*加密终结点与
「看得见流量的盒子」是不是同一台* —— 要分开，先得让会话权威离开
agentd，那是另一个数量级。隧道分帧留插层位置；做的判据：
「agentd 不再需要看内容」的部署真实出现。
（立项的两条理由由此剩一条 —— NAT 最后一公里。已向拍板人确认
顺序仍成立。）

### 安全不变量（评审补的，一条都不许少）

隧道扩大了 controller 被攻破后的可达面：从「同宿主容器 + 少数显式
开放且可达的机器」扩到「全部在线 worker」。**这是本设计最大的一笔
新增风险，必须正视而不是当纯连通性红利。** 五条不变量：

1. **隧道 mutual-auth 只建立传输身份，不授予任何 HTTP 授权。**
   反向路径上 worker 的 `require_auth` 一字不改地继续跑：attach token
   仍与 `attach_allows` 白名单 AND 在一起。「隧道不是入站 root」
   今天成立靠的是**两把 token 分立（inbound / attach）+ AND 白名单**
   这个乘积 —— 拆掉任何一半（比如「传输层已认证，bearer 冗余」这种
   自然到几乎必然的实现简化）就是把 `/local/credential`、
   `/local/mcp/*`、terminal 交给 controller。
2. **controller 永不持有、也无法铸造 worker 的 inbound token。**
3. **`--allow-remote-attach` 的语义原样保留：隧道 ≠ 开放接入。**
   worker 可以只为「被看见、被同步」连隧道，而不接受经隧道的
   `/chat`。开放接入仍是机器主人的一次显式选择（`main.rs` 那段注释：
   「这个进程能跑 shell……那不该是『装上就有』」）——
   隧道时代它一不留神就会变成默认开，评审点名盯防。
4. **开放接入 = 知情同意「远程侧可经模型触发本机执行」。**
   attach 白名单里 `/chat` + `/confirmations` 并存，意味着持有 attach
   凭据的一方能发起一轮并自批确认 —— 这在今天已经如此（这正是
   web 端远程批准自己会话的合法路径），隧道只是扩大了适用范围。
   开关文案要把这句说破，不许含糊成「允许远程查看」。
5. **绑定是 worker 自陈，不是密码学证明 —— 写在明处。**
   同 owner 名下一台被攻陷的 worker 可在心跳里申领该 owner 的任意
   session 并赢得路由。今天这被三重网络闸压着；隧道拆掉网络闸后，
   这条限制必须出现在文档与威胁模型里。（把绑定变成 controller
   签发的可验证凭据是加固方向，与「密钥对身份」同一个触发判据 ——
   见「等判据才做」。）

### 失败模式（评审补的）

- **在线判据 = 应用层 ping/pong deadline，绝不是「连接句柄还在」。**
  桌面 worker 最常见的生命周期事件是合盖睡眠（无 FIN、无 RST），
  内核 TCP keepalive 默认 2 小时 —— 按句柄判，它无限期「在线」。
  子流打开加显式 ACK 超时，保住今天 5 秒快败 502 的语义。
- **重连预算，但 401 不自杀。** 「认证拒 = 停止重连」会把已知的
  401 双义事故（agentd 重启后令牌簿清空，2026-08-18 生产事故）升级成
  worker 永久离线。定案：只对**显式吊销错误码**停下报告；普通
  401/403 走长退避（10 分钟级）无限重试 + 响亮日志。
  重连窗口上限 < min(180, 300) 秒 —— 180 是确认超时（断久了 pending
  确认静默按拒绝），300 是重放缓冲保留期（断久了「刚才那条回答」
  的缝隙重开）。
- **controller 主动重启要发「即将重启」帧**，worker 收到跳过退避立即
  重连；controller 启动后有宽限窗，窗内名册答「未知」而不是
  「不可达」—— 否则每次发版都是一场全设备假故障。
- **「作废在飞请求」只作废 controller 侧的转发流，绝不触碰 worker 侧
  的 Run。** worker 上那一轮必须活过连接换代（现有 detached 设计
  已保证，写成约束防止实现时抄 goose 的 UI 层语义抄过头）。
- **合成错误文案按路由目标分叉。** 现役文案是容器语义（「重新发一次
  会自动把它拉起来」）—— 桌面 worker 断连时那轮**还在跑**，照这句
  重发 = 同一指令跑两遍、文件改两遍（`ChatRequest` 无幂等键）。
  桌面/远端目标要说「会自动接上，不要重发」。
- **阶段 1 带一个最小稳定 id**（`state_dir` 里一个 uuid 文件），
  只用于重连时认出「同一台」以换代作废旧隧道 —— 不做授权依据、
  不落服务端库。幽灵双行**不是**要修的毛病（presence 测试明文
  「这是设计如此」），v1 把它当验收指标是搞错了对象。
- **灰度混版期直拨 + 探活保留**；隧道全量后**删除**直拨路径
  （学 `url_guard` 的处理：没有调用方的代码整个撤，记下从哪个
  commit 捡回），不留一条无人探活的半死路径。

## 不做清单（每条带证据）

| 不做 | 证据 / 触发判据 |
|---|---|
| controller 跑 agent 循环 | `runner.rs` 安全论证 + OpenHands V0 学费。**无判据，永不。** |
| 子 agent 生命周期上移 | 四家（Claude Code、OpenHands V1、goose、MAF）全留在宿主进程。**无判据。** |
| 中心消息 broker / agent 自由互聊 | AutoGen 分布式 runtime 被作者放弃；MAST 36.9%；Cognition。**无判据。** |
| Temporal / durable execution 底座 | 要买的（执行可迁移）靠「账本在 controller」已有；代价全额要付。**无判据。** |
| 桌面/远端 worker 掉线自动换机 | 文件系统身份论证。容器 worker 的 ensure 重建不在此列。**无判据。** |
| `pin_to_worker` / 会话记 worker id | 评审两路致命：会漂的第二真相 + 重装死锁。触发判据：**出现「同 owner 多台机器绑同一会话」的真实纠纷**，且解法先考虑绑定凭据签发而不是钉定 |
| worker 密钥对身份 + WorkerRegistry 落库 | 攻击者模型逐格排空后，没有一个 uuid 挡不住而密钥对挡得住的场景；私钥落盘还违反「够到我机器的钥匙不落盘」原则。触发判据：**要做「controller 签发绑定凭据」的那天**（那时密钥对真承担授权），或第二台常驻远端机器出现 |
| RemoteRunner | `runner.rs` 明文「刻意不预先造第二个 —— 没有真实的第二个部署目标时，抽象只会把当前这一个的形状焊进契约里」；trait 12 个方法对桌面 worker 三分之二无意义或危险（文件 API 伸进用户桌面）。触发判据：**第二个真实部署目标（k8s / E2B）或第一个真实迁移请求** |
| 端到端加密 | agentd 是内容持有方。触发判据：**agentd 不再需要看内容的部署出现** |
| 心跳/在线状态落库 | presence 不进库的理由原样成立。**无判据。** |

## 开发计划

**阶段 0 —— 已做（与本文同一批提交）**：子 agent 工具描述与实际能力
对齐 + 测试钉住「承诺 ⊆ 目录」。

**阶段 1 —— 反向隧道**（唯一的新建设阶段）：

交付物（评审要求逐项有真实调用方，不留「等另一半」空转期）：

1. `cortex-local` 出站 WSS + yamux；agentd 侧隧道终结接进现有
   `sandbox_proxy::forward`（三条纪律原样：纯字节透传、不压缩、
   显式路由清单）
2. 心跳并入隧道 + ping/pong deadline 在线判据
3. 重连：预算 + 换代计数 + 401 不自杀 + 重启帧 + 宽限窗
4. **attach 面的 Local 会话补洞**：`/confirmations` 与 `/runs` 今天
   只查容器（web 对桌面会话答确认会落到指错路的 409）——
   这两条按-worker 路由是「含确认回路」验收的前置，列在本阶段
5. **presence UI**：Flutter 接 `GET /agents?session=`（该端点今天
   0 消费者）——「在哪一台、为什么够不着」的展示落地
6. 合成错误文案按目标分叉；安全五不变量各配一条测试或故障注入

验收：**咖啡馆 wifi 上的笔记本（NAT 后、无 `--attach-addr`），web 端
接入它的会话跑通一整轮含确认回路**；拔网线后 90 秒内界面说清
「在哪一台、为什么够不着」；拔网线时正在跑的一轮在 worker 侧跑完、
重连后结果可见、**用户没有被文案诱导重发**。
故障注入清单：半开连接、agentd 发版重启、401 双义、重连窗口超限、
换代作废不掐 Run。

**阶段 1 之后没有预排的阶段。** 上表每条「触发判据」满足时，
拿着判据回来提案 —— 这不是搁置，是这个仓库对「造好没人调用」
（13+ 次，榜首）的正面回应。
