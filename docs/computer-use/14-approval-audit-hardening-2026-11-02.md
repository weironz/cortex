## 当时确认的问题（历史）

1. 已修复确认簿 deadline 竞态：旧版 `answer` 不检查登记时的 deadline，
   `wait` 还从开始等待时重新计时；事件发送或任务调度延迟时，超期答复
   可能被接受。修复后使用同一个单调截止时间，并移除日志中的确认 token。
2. 默认画面 frame 有效期为 5 秒，用户确认可以等待更久。超过 frame 有效期
   必须拒绝旧动作，但这使正常人工确认很容易失败。当前确认预览中的 frame
   和元素 ref 也是不透明标识，用户难以判断实际目标。
3. 一次性确认 token 最终被压成布尔值，无法把相同请求的批准和动作可靠关联。
   浏览器导航的批准信息没有传入其独立分支的 trace。现有动作确认门禁仍存在；
   审计关联缺口本身不能证明该门禁被绕过。
4. trace 仍在动作后追加；新补丁会对无法准确记录或写入失败的会话标记历史
   不完整，但标记本身的跨进程和跨重启可靠性尚未闭环。驱动可能已经产生副作用，
   此时不能将普通失败解释成“没有执行”，也不能自动重试。
5. 当前部分 trace 用验证参数指纹填充窗口摘要 hash 字段，验证失败也可能被
   归为驱动失败；历史记录不应被解释成真实 verifier 类型或已确认的结果。
6. `latest.json` 的 18 PASS / 2 SKIP 是独立 PowerShell/UIA/CDP 桌面任务，
   并非当前 Cortex 目录、审批、Cua、动作后验证的全链路结果。其中记事本的
   open/read 与 Excel 的读取项也不能单凭现有脚本证明目标文件经应用读取。
7. 动作后帧过期、时钟倒退或 verifier 失败都可能发生在驱动已经执行之后。
   当前已合入同一 run 的跨 backend 写入封锁与关闭协调，尚待主工作区联合
   构建和真实后端验证；它不提供跨 run、跨进程或重启后的持久封锁。
8. 固定的 Cua 0.38 Windows 驱动没有向 Cortex 暴露与元素 token 绑定的
   `IsPassword` 三态证据。当前 Cortex 已在目标 HWND 上直接扫描 UIA
   `CurrentIsPassword`；Unknown 时保守 handoff。自绘控件或第三方 provider
   错报 `false` 时仍可能漏判，上游焦点型 `type_text` 的回退风险也仍需在
   严格输入方案中关闭。

## 当时的实现边界（多数已落地）

- 每次调用分配不可用于授权的随机操作 ID；需要询问时另绑定审批 ID。现有
  一次性 token 继续作为凭据，不写入审计或日志。
- 确认登记、答复、等待和过期列表使用同一个单调 deadline。截止前被原子
  接收的答复不得因等待方调度延迟丢失；超期、伪造和重复回执维持不可区分。
- 真人确认前展示可理解的应用、窗口、控件、动作及验证条件。过期后仅在能
  证明应用、窗口、控件和动作身份一致时重新绑定；角色或标签相同、视觉坐标
  相同均不足以单独证明。无法证明时停止或重新询问，不能静默执行。
- Cua 元素 token 仍没有 `IsPassword` 三态，Cortex 改为在目标 HWND 的 UIA
  Control View 中直接读取 `CurrentIsPassword`，并把 Unknown 当作敏感状态。
  `false` 只表示 provider 如此报告，不能证明没有明文凭据或 provider 一定
  可信。严格输入仍需禁止回退到不同焦点目标。
- 为写动作建立本机持久化账本：在调用驱动前提交审批关联与派发意图，提交
  失败不得调用驱动；派发后超时、中断或终态写入失败必须保留“可能已执行”
  状态，并阻止自动重放。恢复和人工核对的操作也需要持久记录。
- 审计不保存 token、原始输入、URL、截图、密码或剪贴板。关联 ID 与经域
  分离的摘要不等于用户身份，也不证明用户实际看到了界面。
- 新记录和历史 API 必须兼容 v1/v2 严格 DTO。不能把旧记录中含义不准确的
  字段事后改称真实验证结果，也不能让旧客户端把不完整历史显示成完整历史。

SQLite 事务与持久 fence 是可行候选；必须先验证 Windows 本机存储、并发、
同步与损坏恢复，不能仅凭写入返回成功声称断电持久。外部应用与账本没有共同
事务，设计最多能在受控入口内防止同一操作 ID 被重复派发，不能保证外部
副作用“恰好一次”。旧版回滚、账本删除或备份回滚也需独立治理。

## 验收顺序

1. 用虚拟时钟和真实确认簿覆盖迟到、竞争、取消、重放、会话与 token 脱敏。
2. 对账本注入目录不可用、锁竞争、写入与同步失败，并以 fake driver 验证
   派发前故障调用次数为零；验证进程中断后 fence 仍生效。
3. 保留后置验证的真实类型和失败原因；慢动作后重新采样同一时钟域，确认
   过期 frame 被拒而新鲜 frame 可用。
4. 以隔离 Windows fixture 和确定性模型替身驱动真实 `/chat`、工具目录、
   `/confirmations`、Gateway 和 Cua；分别标明自动回执与真人审批。独立 UIA
   或 CDP 只能用于准备和只读验真，不能代替被测动作。
5. 逐项扩展到 Chrome、Notepad、Explorer、Excel 和负坐标副屏；无法证明窗口、
   路径或控件身份时安全跳过。用户提供第二台机器后重复真实桌面测试。
6. 最终代码完成后重跑四小时 soak、完整 Rust/Flutter 检查与安装包验收；
   没有签名证书、双显示器或隔离测试会话时，如实保留相应未通过门槛。

截至 0.1.45，deadline、动作前后迁移验证、完整性门禁、审批 trace、UIA
`IsPassword` 和只读历史 trace 已接入；服务端账号隔离、持久派发账本、真实
人工审批和完整产品链路验收仍未闭环，不能据此宣布生产 GA。
