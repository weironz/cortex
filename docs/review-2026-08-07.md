# 架构复审记录（2026-08-07）

对全部设计做的一次多智能体对抗性复审：8 个维度并行审查（数据模型 / 检索 / 同步 /
服务端栈 / 客户端 / agent loop / 竞争定位 / 创造性提案），65 条发现，12 条重点逐条
由独立怀疑者对抗验证——**9 条 CONFIRMED、3 条 PARTIAL、0 条被驳倒**，其中 3 条
critical 级 schema 缺陷在本机 pg17 容器中实测复现。

## 复审结论：方向没有偏离

核心定位（记忆原生 + 通用 + 多端 + 云同步 + 供应商中立）经竞争调研仍然成立。
以下决策经受住审查，**明确保持，不再复议**：

- axum + sqlx + tokio（唯一保险：DB 访问收敛到 repository 层）
- Postgres + pgvector 单库四路召回，及对 TiDB / Qdrant / Neo4j / ClickHouse 的全部否决
- append-only + 双时间轴 + ULID 的原则本身
- daemon-first；prompt caching 一等公民、不做最小公倍数抽象
- Flutter 六端一套 + flutter_rust_bridge
- 取件 goose-provider-types / goose-providers（正确的依赖面）
- jieba-rs 应用层分词；bge-m3/1024 本地 ONNX
- RustFS + BlobStore trait 可替换设计
- **不引入 HLC / CRDT**——星型拓扑下「服务端定全序 + 客户端单调化墙钟」已覆盖全部需求

## 长期风险（复审确认，定期回看）

1. **RustFS alpha**——已有 disk-full 元数据损坏不可恢复实录。缓解：85% 磁盘告警 + 备份镜像先行 + trait 退路
2. **中文/双时间轴无公开基准**——私有评测集不建，差异化卖点永远「无法证明也无法证伪」
3. **记忆投毒**是已成型攻击类别（MemoryGraft 等）：注入契约只是第一道栅栏，v1 后需专项评估抽取端过滤与来源信任分级
4. goose provider crate 是 alpha、pin rev 自行跟进，成本随供应商数量线性增长
5. 星型拓扑是全部同步简化的前提——引入 P2P 或多 hub 时本页决策全部重评（已写死在 memory.md §九）
6. 「永不删除 + 全量同步」必须对遥测/日志类数据显式豁免，否则观测表拖垮同步
7. 后台管道（转录+抽取+embedding）在低配 VPS 会积压到小时级——最低配置门槛 + 积压告警，否则差评集中在移动端采集体验
8. **一人做六端的总工程量是最大风险**——本次新增的 P0/P1 会进一步压缩 v1 范围，
   建议 v1 明确推迟：Web 端、视频处理、cross-encoder。v1 最小形态 = CLI + 桌面 +
   服务端 + 文本/图片记忆
