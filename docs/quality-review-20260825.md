# 质量回顾 2026-08-25 —— 一轮 12 个 bug 之后

用户一次报了 12 个问题，并问：**为什么这么多 bug？测试要不要加强？架构是不是
设计得不合理？** 这份文档如实回答这三问。结论先行：

> **架构主干没有不合理，12 个病例里只有 1 个是真正的设计缺陷（#11，双进程
> 凭据）。** 其余 11 个里，1 个是测试缺口放走的后端崩溃（#2），10 个是
> UI 侧的工程纪律与交互设计问题 —— 这个分布本身就是诊断：**后端的纪律
> （单一循环、append-only、同生共死判据）是起作用的，而前端没有一套
> 同等强度的纪律。**

本轮病例清单（编号沿用报告顺序）：

## 一、系统性归因 —— 五个根因，不是十二个孤立 bug

### 根因 A：SQL 是运行时校验的，而 CI 里没有一个真数据库
**解释病例：#2**

`crates/cortex-agentd/src/gallery.rs` 的列表查询（第 95–117 行）此刻就带着
这个 bug：SQL 里引用了 `$6`（第 105 行 `NOT $6::BOOLEAN`），而 `.bind()` 只有
五个（第 110–114 行），`$5` 一次都没被引用。Postgres prepare 时要六个参数、
只收到五个 —— 每次打开画廊都是一次运行时报错。

三道本可拦住它的闸，一道都不在位：

1. **编译期检查没启用。** 全仓 109 处 `sqlx::query` / `query_as`（28 个文件），
   用编译期宏 `query!` 的只有 `cortex-store` 的 2 个文件。`justfile` 里
   `db-prepare`（第 138–139 行，生成 `.sqlx/` 离线缓存）这条 recipe **存在但
   `.sqlx/` 目录不存在** —— 又一个「造好了没人调用」。
2. **集成测试在 CI 里静默跳过。** `cortex-store/tests/common/mod.rs` 第 216–226
   行：没有 `DATABASE_URL` 就 `eprintln!("跳过")` —— 而 `ci.yml` 的 test job
   （第 200–223 行）**没有 postgres service**，所以这些测试在 CI 里从来没跑过，
   绿的是空转。这正是 roadmap 里「验证工具自己造出通过」那个形状的又一现场。
3. **agentd 没有 tests/ 目录。** 41 个路由模块（gallery、library、llm、
   model_sources……）没有一条「打一发 HTTP、走一遍真 SQL」的测试。

### 根因 B：UI 状态门控散落各页，没有统一模式
**解释病例：#3、#4、#5**

`app/lib/features/settings/pages/model_page.dart` 是典型：1297 行单文件，
**一个页面级 `_busy` 布尔**（第 72 行）串起全页十几个控件的禁用逻辑
（第 1001 行开关 `onChanged: widget.busy ? null : ...`，第 1047 行拉列表按钮
`onPressed: widget.busy || options.isEmpty ? null : ...`）。任何一个在飞请求、
或 `options.isEmpty` 这种数据态，都会让**不相干的控件**一起变灰，而界面上
没有任何「为什么灰」的说明 —— 这就是 #3 的机理。

#4（已存密钥像空的）与 #5（默认值不可见）是同一根因的另一面：「已保存的
密文」「有默认值的空输入」这类**三态**（未设 / 已设但不显示 / 用户正在改）
没有统一控件，各页各写，写漏一个态就是一个病例。roadmap 里
「三态里的 null 漏掉一个已知事实」记的正是同一形状 —— 它已经在后端咬过
（qwen-image 那次），现在轮到前端。

`app/lib/state/` 下 24 个 controller，各自管理自己的 loading/error/data，
没有共享的 AsyncValue 门控约定，也没有「禁用必有原因」的 lint 或测试模板。

### 根因 C：双进程持有同一把一次性凭据 —— 结构性竞态
**解释病例：#11（唯一的真设计缺陷）**

桌面端是两个进程（GUI + 它拉起的 `cortex-local`）。凭据的分发方式是
**spawn 时一次性快照**：`app/lib/core/local_agent_io.dart` 第 187 行把 token
放进环境变量 `CORTEX_TOKEN` 交给子进程，此后不再更新。而 refresh token 是
**一次性轮换**的 —— `token_store_web.dart` 第 110 行写得很清楚：「同一枚被
出示两次，服务端按重放处理」。

两个前提相乘就是必然事故：**两个持有者 × 一次性凭据 = 谁先用谁作废对方**。
GUI 侧已经把并发续期收敛成一次（`token_store_io.dart` 第 116–117 行的
`_refreshInFlight ??=`），但那只收敛了**同进程内**的竞态；跨进程那条没有
协议，只有快照。这解释了为什么它「历史上多次修而未根除」——每次修的都是
某一条具体竞态路径，而结构（两个独立持有者）没变，新路径就会再长出来。

### 根因 D：「能力与界面同生共死」的纪律只覆盖了 agent 能力，没覆盖产品功能
**解释病例：#1、#6、#9、#10**

这条纪律在 agent 侧是有闸的、且真的起作用（`Caps.has_skills` 一处判据同时
决定提示词与工具目录；`deployment_ok` 在 llm.rs 里只算一次）。但它保护的是
「模型看到的能力目录」，**没有对称的一条保护「用户看到的功能目录」**：

- #1：建号能力存在（`cortex-agentd --create-user`，accounts.rs 第 735–744 行
  连报错文案都写了这条路），而登录页上没有入口也没有说明 —— 服务端有、
  界面没有，就是「造好了没人调用」在产品层的表现。
- #6：终端 ANSI 渲染 2026-08-17 就做完了（roadmap「富文本四件套最后一件」），
  右栏那个「终端」却不是真终端 —— 展示能力与交互能力脱节。
- #9、#10：竞品的常规功能（资源管理器打开、fork 会话）没有进任何清单。
  roadmap 的 I/J 两节证明「逐项对照核代码」这个方法有效（15 条全落地），
  但那是**一次性的**，不是每版都跑的闸。

### 根因 E：功能先行，交互设计滞后且无回归走查
**解释病例：#7、#8、#12（以及 #4、#5 的表现层）**

设计稿是 2026-08 补做的（git log：「按设计稿重构 Web 与桌面 UI」「设计稿与
落地清单入库」），也就是说大量界面是**先长出来、后补设计**。补做那次收掉了
40 项，但之后新增的界面（模型选择弹层、右栏页签、主题切换）又回到了
「功能先行」的节奏 —— #12 弹层遮挡聊天区、#7 图标位置、#8 收起交互不一致，
都是没有过设计走查就发出去的。这不是能力问题（八维度审查那次证明走查
有效），是**走查没有成为发版流程的一部分**。

### 归因小结

| 根因 | 病例 | 性质 |
|---|---|---|
| A · SQL 无编译期检查 + CI 无真库 | 2 | 测试缺口 |
| B · UI 门控/三态无统一模式 | 3、4、5 | 工程纪律 |
| C · 双进程一次性凭据 | 11 | **设计缺陷** |
| D · 功能目录无「同生共死」闸 | 1、6、9、10 | 工程纪律 |
| E · 交互设计走查未入流程 | 7、8、12（+4、5 表现层） | 流程缺口 |

## 二、架构是不是设计得不合理 —— 如实区分

### 对的部分，且本轮 12 个病例反过来印证了它们

**① 单一 agent 循环。** 本机与容器是同一个 `cortex-local`
（`--exec-env=container` 一个开关），第二份实现删掉的理由记在
architecture.md：「漏改的那一份不会有任何测试红」。**本轮 12 个病例里没有
一个是「两份循环漂移」类** —— 而这恰是同架构产品最常见的一类 bug。纪律
生效的证据是病例的缺席。

**② append-only + ULID 游标。** gallery.rs 第 58–68 行按 `id` 翻页的论证
（「那个失败模式压根不存在了」）是这套数据模型的缩影：一整类翻页重复/漏行
bug 被构造性消灭。本轮没有任何数据丢失/错乱类病例。

**③ 判据只算一处。** `deployment_ok` 在 llm.rs 只算一次、`Caps.*` 一处判据
管两个出口 —— 2026-08-21 那次「能关这句话是假的」修完之后，同类没有复发。

**④ 边缘分流、供应商层取件、凭据不进 CI。** 本轮没有部署类、供应商适配类
病例 —— 对照 roadmap-done 里那段密集的部署踩坑史，这几块已经稳定下来了。

### 在反复出血的部分

**① Flutter 状态层（`app/lib/state/` 24 个 controller +
`features/settings/pages/` 各页）。** 证据见根因 B。这不是架构错 ——
Riverpod 分层本身没问题 —— 是**没有把后端那套「形状清单」纪律翻译成前端
控件规范**。roadmap 那张表 13 个形状里「在飞请求不作废」「三态 null」
「空串顶掉默认值」在前端全部有对应物，但前端没有对应的闸。

**② agentd 的 SQL 层（41 个路由模块、109 处运行时 SQL）。** 证据见根因 A。
工具链（sqlx 宏、db-prepare）都在手边，只是没接上。

**③ 双进程凭据分发（唯一该改设计的地方）。** 「桌面端两个进程」这个结构
本身是对的（GUI 崩了 agent 还在跑、agent 崩了 GUI 拉起它），错的是**凭据
协议**：一次性轮换凭据不允许有两个独立持有者。修法不是再堵一条竞态路径，
是让 `cortex-local` 不再持有长期凭据 —— 要么远端调用全部经 GUI 代理，
要么 GUI 给它发短期票据、由 GUI 单点续期（与 agentd 的委托令牌同形状，
这个仓库已经会做这件事了）。

### 回答原话：「是不是设计的不合理」

**不是。** 进程划分、数据模型、依赖方向、能力判据这些**架构级决策**在本轮
12 个病例里只贡献了 1 个（#11），且那 1 个也不是分层错了，是层间的凭据
协议没设计。其余 11 个的分布指向的是另一件事：**这个仓库的质量纪律是在
后端的血泊里长出来的（roadmap 那 13 个形状全是后端/运维现场），前端还没
流过足够的血去长出自己的清单** —— 而这轮 12 个里 10 个是前端，正是补课
通知书。把它们读成「架构不合理」会修错地方。

## 三、分层测试增强方案

按「本轮拦截数 / 成本」排序。每条注明它本会拦下哪些病例。

### 1. agentd + 真 PG 的集成测试常态进 CI（拦截：#2）

现状：`ci.yml` 的 `cargo test` 没有 postgres service，`cortex-store` 的 PG
测试静默跳过（common/mod.rs:222「跳过：未设置 DATABASE_URL」），
`cortex-agentd` 连 tests/ 目录都没有。

做法：
- `ci.yml` test job 加 `services: postgres:17-alpine`，设 `DATABASE_URL` ——
  **现有的** tenant_isolation / sync_ordering 等五个测试文件立刻从「从不跑」
  变成「每次跑」，零新代码；
- 新建 `crates/cortex-agentd/tests/routes_smoke.rs`：起一个真 `AgentState` +
  真 PG，对每条带 SQL 的路由至少打一发（gallery、library、model_sources、
  export、search……）。**gallery 的 bind 崩在第一发就红**；
- ⚠️ 按「验证走的不是用户那条路」的教训：smoke 必须走 HTTP handler 整条路
  （axum `Router` + `tower::ServiceExt::oneshot`），不许直接调内部函数。

成本：一天量级（service 半小时，smoke 骨架一天）。这是性价比最高的一条：
它同时给 A 根因和「CI 空转」两个问题上闸。

### 2. sqlx 编译期检查，或退一步的 QueryBuilder 纪律闸（拦截：#2）

首选：把 agentd 里**字面量 SQL**（绝大多数，gallery/library 全是）迁到
`query!` / `query_as!` 宏 + `.sqlx/` 离线缓存。recipe 已有（`just db-prepare`），
CI 加一步 `cargo sqlx prepare --check --workspace` —— 缓存过期即红。
bind 数不匹配从此是**编译错误**。

次选（若嫌 109 处迁移太贵）：只迁 agentd 的查询路径（~70 处），并加一条
lint 闸：`scripts/` 里 grep「`format!` 的结果流进 `sqlx::query`」按行报错 ——
动态拼 SQL 一律走 `QueryBuilder::push_bind`。⚠️ 按 lint-sh 的教训，这道闸
上线前先做故障注入：手写一处违规，确认它红；写进注释，确认它不红。

成本：宏迁移 2–3 天（好消息是现有 SQL 都是静态形状，`$n IS NULL OR` 模式
本来就是为避免动态拼而写的，迁移是机械的）；CI 闸半小时。
与第 1 条重叠但不冗余：宏拦在编译期、smoke 拦运行期语义（JOIN 错列这种
宏拦不住的）。

### 3. Flutter「三态/门控」控件规范 + widget 测试模板（拦截：#3、#4、#5）

做法：
- 抽三个共享控件进 `app/lib/widgets/`：
  - `AsyncActionButton` —— 自带 per-action 在飞状态（**不共享页面级 `_busy`**），
    禁用时必带 tooltip 说明原因；
  - `SecretField` —— 「已保存」态显示掩码占位 + 「已保存，输入以替换」文案，
    与「空」态在视觉上分得开；
  - `DefaultedField` —— 有默认值的输入框把默认值显示成可见的 placeholder +
    「默认」徽标，不是空白。
- widget 测试模板（tests 里已有 66 个测试文件与 `support/replay_api.dart`
  这套共享假后端，模式是现成的）：每个新设置页必须有一条
  「三态各渲染一次 + 禁用控件都能找到原因文案」的测试；
- 迁移 model_page.dart 的门控到 per-action：第 1001/1047 行那种
  「一个 `_busy` 灰全页」拆开。

成本：控件 + 模板 2 天，存量页面迁移随手做（每页半小时）。这条不只拦本轮
三个病例，它把根因 B 的**类**关掉 —— 下一个设置页默认就长对。

### 4. auth 状态机的模型测试 + 凭据协议修正（拦截：#11）

先测后改：
- 把「两个持有者 × 一次性轮换」写成一个纯 Dart/Rust 状态机模型测试：
  参与者 {GUI, local-agent}，动作 {用 access、access 过期、发 refresh、
  轮换落库、进程重启}，断言「任何交错下不出现双方都持作废凭据」。
  **现状建模必然找出反例** —— 那个反例就是回归测试；
- 修协议（这是第二部分里点名的设计修正）：`cortex-local` 不再经
  `CORTEX_TOKEN` 拿长期凭据，改为 GUI 发**短期票据**并单点续期 ——
  与 agentd 的委托令牌同一形状，仓库里有现成参照（`delegated_token.rs`）；
- 桌面端集成测试补一条「GUI 轮换后 agent 的下一个请求不 401」。

成本：模型测试 1 天；协议改动 3–5 天（跨 app/ 与 cortex-local 两块，按
CLAUDE.md 并行策略这种活串行做）。**这是 12 个里唯一「多次修而未根除」的，
根除只能走这条，再堵单条路径就是第 N+1 次修而不根除。**

### 5. 「功能目录走查」发版闸（拦截：#1、#6、#7、#8、#9、#10、#12）

这 7 个病例没有一个能被自动化测试拦住 —— 它们是「缺一个入口」「交互不一致」
「排版差」，判据在人眼里。但 I/J 两节已经证明**清单式走查**对这类问题有效
（15 条全落地）。把它从一次性变成常态：

- `docs/design/` 里维护一份**功能目录清单**（登录/注册、会话操作全集、
  右栏三页签、设置各页），每项两列：服务端有没有 / 界面有没有。两列不齐
  就是一行待办 —— #1 那种「`--create-user` 有而登录页没说」在清单上是
  一眼可见的不齐；
- 发版前（`just release-check` 里加一步人工确认项）过一遍：新功能的
  设计走查做了没有、弹层/浮层在最小窗口尺寸下试了没有（#12 就是这一条）；
- 竞品对照（#9、#10 这类）每季度重跑一次 I 节那种「逐项核代码」的对照，
  而不是等用户报。

成本：清单初建半天，每版走查十几分钟。**拦截率最高的一条**（7/12），
成本最低，但它是流程不是代码 —— 靠的是把它写进 release-check 让人跳不过。

### 6.（横切）每道新闸先做故障注入自检

roadmap 已记录三次「验证工具自己造出通过」。上面第 1、2、5 条每道新闸
上线时执行同一仪式：**先人为制造一个它该拦的错误，看它红；再把错误藏进
注释/文案，看它不红** —— 然后才算上线。这条没有独立成本，它是其他条目的
验收标准。
