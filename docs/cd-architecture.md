# 持续交付：这条流水线是怎么设计的

**这份文档给两种人看**：一是接手本仓库发布/部署的人，二是**别的项目**想把
这套做法搬过去的人。

它讲的是**为什么这么设计**。具体怎么发一版见 [release.md](release.md)，
线上那台机器长什么样见 [deploy.md](deploy.md)，装到自己机器上见
[install.md](install.md)。

> **每一条设计决策后面都有一次真实事故或一次实测。** 没有事故垫背的规则
> 写在这里只是意见，读的人分不出哪些能删。所以下面凡是「必须」，
> 都会说清**不这么做时会发生什么**，以及那件事**为什么当时没人发现**。

---

## 一、三条流水线，各回答一个问题

```
              ┌──────────────────────────────────────────────┐
  push/PR ───►│  CI (ci.yml)         这次改动本身对不对       │
              │  fmt · clippy · 测试 · Flutter · 三平台构建   │
              └──────────────────────────────────────────────┘
                                  合并到 main：**什么都不部署**

              ┌──────────────────────────────────────────────┐
  git tag ───►│  Release (release.yml)   这一版发得出去吗     │
   v0.1.20    │                                              │
              │  preflight ──┬── build    (Windows 二进制)    │
              │   版本一致   ├── desktop  (Inno 安装程序)     │
              │   凭据泄漏   └── image ×4 (docker，两个 registry)│
              │   CHANGELOG        每个产物都被真的运行过一次  │
              │        │                                     │
              │        └──► release  汇总校验和 · 产物清点    │
              │                └──► deploy ────────┐         │
              └────────────────────────────────────│─────────┘
                                                   ▼
              ┌──────────────────────────────────────────────┐
 手动触发 ───►│  Deploy (deploy.yml)   把某一版放到线上        │
 （回退用）   │                                              │
              │  ansible/ 取**默认分支** · compose 取**那个 tag**│
              │        │                                     │
              │        ▼  ssh + ansible-playbook             │
              │   ┌────────────────────────────────────┐     │
              │   │ 节点 /data/cortex                   │     │
              │   │  .env         ← ansible 每次渲染    │     │
              │   │  .env.secrets ← **人工写一次**       │     │
              │   │  docker-compose.yml ← ansible 送    │     │
              │   └────────────────────────────────────┘     │
              │        │                                     │
              │        ▼  从**外面**打 https 验五条硬断言      │
              └──────────────────────────────────────────────┘
```

**三条各自的判据不同，这是整套设计的骨架**：

| | 触发 | 它回答什么 | 失败的代价 |
|---|---|---|---|
| CI | push / PR | 这次改动对不对 | 拦在合并前，最便宜 |
| Release | 推 `v*` tag | 这一版**发得出去**吗 | 产物已经进 registry，撤不回来 |
| Deploy | Release 调用 / 手动 | 线上换成这一版 | 用户当场受影响 |

## 二、决定点只有一个：`git tag`

早期这里是「发布产出产物，部署**只能手动触发**」，理由是「哪个版本在线上
是人做的决定，不该是合并的副作用」。前半句对，后半句推错了一步：

**打 tag 本身就是那个决定。** 让人打完 tag 之后再记得去点一次部署，多出来
的不是安全，是一个会被忘掉的步骤 —— 而忘掉的表现是「发了但线上还是旧版」，
**没有任何红灯**。

所以现在：

- `on: push` 到 main —— **什么都不部署**（这一条没变）
- 推 `v*` tag —— 构建 → 发产物 → **接着上生产**，一条龙
- `workflow_dispatch` 保留着，但它的用途变成**回退**：把线上换成某个更早的
  版本。那与「发新版」是完全不同的一件事，不该只能靠再打一个 tag 来做

> **可搬**：把「人的决定」落在一个**不可变、可审计、可回溯**的东西上
> （tag / release），而不是落在一次点击上。点击留不下痕迹，也会被忘记。

### `needs: release` 而不是 `needs: image`

产物没发成功就不该上生产。**「线上是新版、下载页是旧版」比两者都旧更难解释** ——
用户报障时你们看到的版本号对不上，而两边都「成功」了。

## 三、闸门放在最前面

`release.yml` 的第一个作业叫 `preflight`，**所有其它作业 `needs` 它**。它做
三件事：版本号一致、CHANGELOG 里有这一版、没有疑似凭据的文件。

为什么非要排在最前：**版本号对不上时，最不该发生的事是先花二十分钟在几个
平台上编译出一堆名字是错的产物。**

同样的形状在 ansible 那侧重复了一次 —— `deploy.yml` 把全部前置断言
（版本号格式、`.env.secrets` 在不在、目标机有没有 `python3-requests`）
放在**任何写操作之前**：

> 半途才发现前提不成立，意味着 `.env` 已经被改写、而服务还没起来 ——
> **那比一开始就拒绝糟得多**。

> **可搬**：闸门的位置比闸门本身重要。一道放在末尾的检查，拦住的是
> 「浪费」；放在开头的同一道检查，拦住的是「半应用的状态」。

## 四、产物：编译得过 ≠ 跑得起来

**每一样发出去的东西都必须被真的运行过一次。** 这条是拿事故换的：

| 产物 | 冒烟做什么 | 它抓的是 |
|---|---|---|
| 裸二进制 | 逐个跑 `--version` 并核对版本号 | 动态链接（`GLIBC_2.xx not found` 这一类） |
| 桌面安装程序 | **真的启动一次 GUI**，几秒内没自己退出才算过 | 缺 DLL —— 那种产物会一路通过打包上传，直到第一个用户下载才暴露 |
| `cortex-agentd` 镜像 | `docker run --rm img --version` | 同上，且证明版本号真的编进去了 |
| `cortex-sandbox` 镜像 | `--version` + `git/python3/node` 三样都在 | 「沙箱起来了但干不了活」 |
| `cortex-egress-proxy` | scratch 镜像没有 shell —— 只能真跑起来看它有没有开始监听 | 起不来 |
| `cortex-web` 镜像 | `/healthz` + 首页有 `<html>` + **深链接也回 `<html>`** | SPA 回落没配 |

打包与校验都在 `scripts/release-*.sh` 里，**本机可以真跑**。YAML 里只剩
「在哪台机器上编译」。这不是洁癖：一段只在 CI 里存在的逻辑，改它的唯一办法
是推一次 tag 试试。

### 产物清单必须是显式的

`release` 作业里有一段「产物清点」，逐个点名。少一个当场红。

不点名会怎样：release 照样建得出来，只是那个平台的用户在下载页上**没有
东西** —— 而没有任何红灯。

同一条纪律的另一半在 `download-artifact` 上：**必须给 `pattern`**。不给
时它下载全部产物，而 `docker/build-push-action` 会顺手上传两个 0 字节的
`*.dockerbuild` 溯源记录 —— 那两个下不下来，报的却是
`Artifact download failed after 5 retries`，看上去像网络抖动（我们据此重跑
了两次，两次都同样失败）。

> **可搬**：发版产物应当是一份**显式清单**，不是「把桶里的东西全拿走」。
> 后者会让任何一个 action 顺手上传的东西变成发版的一部分。

## 五、镜像

### 只打具体版本，**不打 `latest`**

生产钉死版本，重启之后必须回到同一个。一个会漂移的 tag 会让
「线上跑的是哪一版」变成一个**查不清**的问题。

### 推两个 registry

一个是生产实际拉取的（节点在国内 → 阿里云 ACR），一个是异地副本
（Docker Hub）。

> 挑镜像站的坑值得单独记：第三方 Docker Hub 镜像站会缓存 `tag → digest`，
> 那是「**拉到旧镜像还看不出来**」的陷阱 —— `docker pull` 说成功，
> digest 却是上一版的。

### `provenance: false` —— 一条环境漂移咬出来的

buildx 默认给镜像挂一份 provenance 证明，结果是一个 OCI index，里面带一个
`application/vnd.oci.empty.v1+json` 的空描述符 —— **阿里云 ACR 不认这个
media type**，push 直接 `denied: unknown manifest class`。

这条最难查的地方在于：0.1.7 发的时候还没事，中间 runner 上的 buildx 升了
一版。四个镜像会一起挂，**看起来像我们改坏了什么** —— 而本地
`docker build` 一路绿灯，因为它根本不 push。

> **可搬**：凡是「本地能过、CI 挂」的东西，先怀疑**只有 CI 才走的那一步**
> （push / 上传 / 签名），以及 runner 镜像里那些没被钉版本的工具。

### git sha 进镜像，而不是只靠版本号

`.dockerignore` 把 `.git` 挡在构建上下文外面，所以容器里问不出提交号 ——
由 CI 用 build-arg 送进去，落进 `/health` 的 `commit` 字段。

**判「线上有没有某个修复」靠的是它，不是版本号** —— semver 打完 tag 的
下一秒就不再唯一（2026-08-21 踩过：同一个 `0.1.x` 对应过两个不同的构建）。

## 六、部署：两条时间线，故意不对称

这是整份文档里**最容易照抄错**的一条。

| 取什么 | 从哪取 | 为什么 |
|---|---|---|
| `ansible/`（部署机制） | **默认分支** | 修了一个部署 bug，不该只有以后的版本受益 |
| `deploy/docker-compose.yml`（编排） | **那个 tag** | 一个版本应当被部署到它一起发布的那份编排上 |

第一版把两者都挪到了 tag 上，后果不只是「新东西在老 tag 上不存在」，
而是**回滚到任何早于 ansible 改造的版本都会失败**：

```
[ERROR]: The requirements file 'ansible/requirements.yml' does not exist.
```

### `ref:` 不能省 —— 同一天撞的第二次

`actions/checkout` 不写 `ref` 时取的是**触发工作流的那个 ref**，而这个
workflow 有两个入口，它们的 ref 不一样：

- `workflow_dispatch`（手动）→ main　　← 只验了这一个，通过
- `workflow_call`（release.yml 调）→ tag　← 发下一版时炸在这里

**`workflow_call` 那条路只有真发版时才走得到，手动跑一百次也验不到它。**
所以现在有一道断言专门盯着「`ref:` 真的生效了」：确认 HEAD 是默认分支、
确认 `ansible/deploy.yml` 真的在。

它防的第二种更隐蔽：`github.event.repository.default_branch` 取到空值时，
checkout 会**悄悄 fallback** 到触发 ref —— 日志一切正常。

> **可搬**：一个有多个入口的 workflow，**每个入口的隐式上下文都不一样**。
> 凡是「只有某个入口才走得到」的分支，给它一道自检；否则你验证的永远是
> 另一条路。

## 七、凭据：不经过 CI

节点上的 `.env` 拆成两份，compose 两份都读
（`--env-file .env --env-file .env.secrets`）：

| | 谁维护 | 内容 |
|---|---|---|
| `.env` | ansible 渲染，**每次部署覆盖** | 版本号、域名、上限、开关 |
| `.env.secrets` | **人工写一次**，ansible 从不碰 | 10 个凭据 |

**为什么**：部署那把 SSH 密钥已经在 GitHub Secrets 里，再把凭据也放进去
等于多开一个入口 —— 一个恶意 action 能把 secrets 一次性 dump 走。

ansible 只**检查它在不在**，不在就停在那里并指回装机 playbook。

### 安全模型要说实话

那把部署密钥**等于节点 root**。它曾经不是（节点上用
`command="..."` forced command 钉死，CI 只送 compose 的 sha256 不送文件），
改成 ansible 之后那道限制撤掉了 —— ansible 要把模块推过去执行，
任何 forced command 都会挡住它。

**为什么可以接受**：那道闸挡住的比它看起来少。compose 把
`/var/run/docker.sock` 挂进编排服务，而它的镜像 tag 由 CI 决定、registry
推送凭据就在同一个 Secrets 里 —— **一次 Actions 沦陷早就等于节点 root**
（推个恶意 `:v9.9.9` 再部署它即可）。那道闸真正还挡得住的只有
「单独泄露 SSH 密钥」这一种。

换来的是：compose 与 `.env` 由 ansible 送，不再要人带外 `scp`。此前改一次
compose 就得手动同步，忘了的表现是**流水线跑二十多分钟最后一步红**。

> **可搬的不是这个结论，是这个方法**：把一道闸拆掉之前，先算清楚它**实际**
> 挡住了哪条路径。很多闸门的价值是象征性的，而维护它们的成本是真的。
> 真想把「Actions 沦陷 ≠ 节点 root」拿回来，该做的是把 registry 凭据换成
> OIDC + 云厂商的临时角色，而不是守 compose 那道门。

## 八、部署过程里的四道闸

### 1. compose 里每个服务都必须有归宿

`deploy.yml` 跑一次 `docker compose config --services`，把结果与
「这次要部署的服务清单 + 显式排除清单」比对，有落单的当场拒绝。

**「往 compose 里加了服务却没人启动它」这个形状犯过三次**（一次险些、
一次漏了一整轮发布、一次让某版上线后回滚）。症状是沉默的：部署全绿，
只是那个服务从来没被启动过。

> **可搬**：凡是「声明的清单」与「执行的清单」分居两处的地方，
> 加一条「两边必须对齐」的断言。人对齐不了，程序可以。

### 2. 库先起来并等它真健康

主体那一步带 `--no-deps`（只动点名的服务，不碰同机上别的栈），而
**`--no-deps` 会让 compose 忽略 `depends_on` 的健康等待** —— 应用会在库
还没接受连接时启动，而它起来第一件事就是跑 migration。

表现会是「部署输出全绿，但服务在反复重启」，或者更糟：健康检查窗口恰好
等到它重启成功，于是**这次没事、下次冷启动慢一点就有事**。

所以库单独先起一次并 `wait: true`。

### 3. 失败走 `rescue` 回滚，并说清什么**不会**回滚

任何一步失败都回滚（不只是健康检查失败那一种）—— 因为
`docker compose pull` 一失败就中止，而那时 `.env` 已经被改写了。
部署一个 registry 里根本不存在的版本，会留下一个指向它的 `.env`：
**容器还在跑旧的（所以看着一切正常），但持久化的期望状态已经坏了，
下一次重启就会去拉一个不存在的 tag。**

回滚之后那条失败消息里写着一句**必须写的话**：

> ⚠️ 数据库 schema **不会**回滚 —— migration 只前滚。

不写的话，「已还原到上一版」会被读成「什么都没变」。

### 4. 保留最新 N 个版本的镜像

回滚要靠**本地已有的**上一版镜像 —— 它不需要 registry，也就在 registry
挂掉时仍然可用。清理按**版本号**排序而不是按创建时间：镜像是按拉取顺序
到的，一个被重新拉过的老版本会显得「最新」。

## 九、验证：不信部署脚本自己的报喜

部署跑完之后，CI **从公网**打 https 做五条硬断言。

理由：脚本说健康只代表容器的 `HEALTHCHECK` 绿了，**证明不了反向代理的
路由、路径改写、证书这一整条链路是通的**，更证明不了线上跑的真是这一版。

五条各自对应一种「看起来正常、其实在服务假数据」的失败：

| 断言 | 不查会怎样 |
|---|---|
| `version` 是这次部署的那个 | 部署「成功」了但跑的是旧版 |
| `role` 是期望的那个服务 | 反向代理的分流配错，答话的是另一个进程 |
| `auth` 是开着的 | 一个认证关闭的线上实例把整个库交给任何能连上的人，**这件事没有任何别的症状** |
| `database` 真的接上了 | 少一个环境变量就整个回落到 mock 数据源继续启动 —— `status: ok`、docker 转 healthy，**而它在服务假数据** |
| `blob_backend` 真的是对象存储 | 凭据不对时回落到本地文件系统：上传的媒体只存在容器里，不进备份、签不出链接 |

> **`"status":"ok"` 与 docker 的 `HEALTHCHECK` 都不代表接上了后端。**
> 这是本仓库最贵的一条经验：健康检查要断言的是**依赖真的接上了**，
> 不是「进程还活着」。

### 能力下线时，断言要跟着下线

这条验证里曾经有一句 `memory_reachable: true`。那个能力整条拆掉之后字段
也从 `/health` 里删了 —— 于是这条断言在之后的每次部署上**必然失败，
而部署本身是成功的**。

代码里已经有单元测试钉住「这两个字段不存在」，只有部署验证漏了。
**同一条纪律的两处，改了一处。**

## 十、几条与「快」有关的，都不显眼

- **`concurrency` 排队而不是取消。** 两次部署同时跑会在节点的 `.env` 上
  打架。**半应用的部署比慢的部署更糟。**（CI 那条相反：`cancel-in-progress:
  true`，因为它没有副作用。）
- **`RUSTFLAGS` 不放顶层 env。** 缓存工具把 `RUST*` 环境变量算进缓存键，
  而发布流水线不设这个变量 —— 于是同一台 runner 上编同一份代码的两个作业
  永不共享缓存（实测：发版的 Windows 作业 `No cache found.`，冷编 14.4 分）。
  **而且硬凑成一样也没用**：cargo 自己的 fingerprint 同样含 `RUSTFLAGS`。
- **发版作业与 CI 作业要共用同一个缓存键。** 一次运行只能读「本 ref 的 +
  默认分支的」缓存，而两个 tag 是**兄弟 ref** —— 上一个 tag 存下的东西，
  下一个 tag 永远看不见。唯一能命中的来源因此只剩 main 上 CI 存的那份。
- **构建目标（`--target`）也要一致。** 带不带 `--target` 在 cargo 眼里是
  两个输出目录、两套指纹。缓存「命中」了、编译产物一个都没用上 ——
  **那是最难发现的一类浪费：每个指标看起来都是绿的。**

## 十一、想搬到别的项目：从哪开始

按「买到的东西 / 花的力气」排，前四条几乎无成本：

1. **前置闸门**：版本一致、变更日志有这一版、没有疑似凭据文件。
   放在**编译任何东西之前**。
2. **每个产物冒烟跑一次。** 一行 `--version` 就能挡住整类动态链接问题。
3. **显式产物清单 + 少一个当场红。**
4. **部署后从外面验证**，断言里必须有「依赖真的接上了」，不能只有
   `status: ok`。
5. **凭据与配置分成两份文件**，只有配置那份由自动化渲染。
6. **决定点落在 tag 上**，让部署跟着发布走，别留一个「还差最后一步」。
7. **部署机制与应用版本分成两条时间线**（机制取默认分支，编排取 tag）。
8. **回滚路径要被验证过**，而且必须说清「什么不会回滚」（schema、
   已发出的消息、已扣的钱）。

### 别照抄的部分

这些是本仓库特有的，搬过去只会误导：

- **具体的 registry 与域名**（阿里云 ACR、traefik 的分流规则、
  `/api` 的 StripPrefix）
- **只发 Windows 桌面安装程序**：那是按三个平台各自的拦截强度做的取舍
  （Windows SmartScreen 是警告、macOS Gatekeeper 是硬拒绝、Linux 要自建源），
  不是通用结论
- **健康检查里那几个字段名**（`role` / `blob_backend` / `commit`）——
  形状可搬，名字不行
- **「一次 Actions 沦陷等于节点 root」的接受** —— 那是**在这个威胁模型下**
  算过账的结论。你的账不一定这么算
