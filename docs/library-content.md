# 什么东西有资格进资料库

> 本文档回答**判据**，不回答资料库怎么实现（那在 `crates/cortex-agentd/src/library.rs`
> 的头注释里）。写下来是因为「为什么是这个判据」在提交信息里留不住，而这件事
> 每加一种产物就会被重新问一遍。

**结论先说：不做「这是不是交付物」的判断。** 上传的、生成的，全收；膨胀靠配额、
搜索、删除来管。理由在 §三。

---

## 一、这个问题是怎么来的

2026-09-02，用户问「生成的图片为什么不会显示在资料库里」。查下来资料库
**什么都进不去**：服务端 `POST /library` 完整，客户端 `addToLibrary()`
零个调用点，生产上 `library_items` 0 行、`generated_images` 8 行。

接上生成图那条路之后，他追问了两句，两句都问在点子上：

1. 「自动收进资料库了为什么还要右键存进去呢，不是多此一举吗」
2. 「除了图片，用户在会话里要求主动生成的产物都要存进资料库吧，比如帮我生成
   一个方案，输出一个 excel、ppt 等等，除非是存本地工作区的 —— 所以这里有个
   问题，生成的内容哪些要存到资料库，有可能是直接落到本地盘的，这种应该不能
   存在资料库，不然资料库就膨胀了」

第二句里那个判据是**「落哪个盘」**。下面说明为什么它不成立，以及别人用的是什么。

---

## 二、别人怎么做的（2026-09 调研）

### ChatGPT 资料库 —— 不判断，全收，配额兜底

* 自动存**两样**：用户上传的文件 + ChatGPT **生成的**文件，跨会话可复用
* **生成的图不在这一栏**，单独去「图片」—— 与 Cortex 现在的分法一一对应
* 明确排除：临时聊天里的文件
* 膨胀不靠判断，靠**配额 + 手动删**：Free 500 MB / Go 4 GB / Plus·Business
  20 GB / Pro 100 GB。删对话**不删**资料库里的文件；删文件在设置 → 存储

来源：[File storage and Library in ChatGPT](https://help.openai.com/en/articles/20001052-file-storage-and-library-in-chatgpt)、
[the-decoder 的报道](https://the-decoder.com/chatgpt-simplifies-file-management-with-new-toolbar-and-library-tab/)。

### Claude Artifacts —— 判断在「生产那一刻」

判据是**内容的形状**：自成一体、超过约 15 行代码、用户可能想在聊天之外保存
/编辑/分享、脱离上下文还能复用。每次编辑存一版，可回滚、可选择分享哪一版。

关键的一句：**artifact 就是交付物本身，不是交付之后再去别处生成的东西。**

来源：[What are artifacts and how do I use them?](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)。

### 两家的共同点，比差异更重要

**谁都不扫工作区、不扫磁盘。**

ChatGPT 的 code interpreter 生成的文件之所以进资料库，是因为那些是**回给用户的
下载产物**，不是留在容器里的中间文件。Claude 的 artifact 之所以是 artifact，是
因为模型在生成时就把它写进了那个容器，而不是事后从某个目录里被捞出来。

所以「落哪个盘」这个判据两家都没有用过 —— 它们根本不面对这个问题。

## 三、Cortex 的定论

### 判据不是「落哪个盘」

落哪个盘是**实现细节**。同一份方案，模型这次 `write_file` 到工作区、下次直接把
内容回给用户，取决于它当时挑了哪个工具。拿这个当判据，结果是「同样的东西昨天
进了今天没进」，而用户完全看不出规律 —— 一个没有规律的规则等于没有规则。

真正的分界是**有没有一个「交给你」的动作**。这个判据不需要扫盘，也不需要模型
自己评估重要性。

### 不做「是不是交付物」的判断

代价是不对称的：

| | 出错的样子 | 能不能补救 |
|---|---|---|
| 全收（膨胀） | 列表里有用不上的东西 | **能** —— 搜索、配额、删除，三样都是成熟手段 |
| 判断（漏收） | 该在的东西不在 | **不能** —— 用户不知道去哪找，甚至不知道有东西没被存 |

膨胀是**已经被解决的问题**。漏收解决不了。两家都选了不判断，这不是偷懒。

⚠️ 尤其**不能把这个判断交给模型**。工具目录摆什么它就会去调什么（见 CLAUDE.md
不可违反的约束 §2），而它对「这是不是交付物」的判断一贯偏松 —— 结果是资料库被
灌满，`library_search` 的信噪比跟着一起垮，而那正是资料库唯一的用途。

### 三条路各自怎么走

| 东西 | 判据 | 怎么进 |
|---|---|---|
| 生成的图 | 一次调用只产出这一件，就是用户要的 | **自动**（2026-09-02 已做，`image::record_in_library`） |
| 用户上传/粘贴的文件 | 用户主动给进来的 | **自动** —— 与 ChatGPT 一致 |
| agent 写到工作区的文件 | 那是工作区的内容，不是交付物 | **不进**。要进得先有一个「交给你」的动作 |

第三行是关键：`write_file` 写出来的二十个文件里十九个是脚本、临时 csv、build
产物。它们不进资料库不是因为「落了本地盘」，是因为**没有人把它们交出来**。

### 图和 pdf/docx 进来之后检索不到，这件事要说出来

服务端对 `image/*` 与提不出正文的类型落 `chunk_state = 'unsupported'`，
`library_search` 永远找不到它们。全自动收进来之后列表里会有一批这样的条目 ——
资料库那一屏为此专门用了琥珀色，收进去的那一刻也要当场说清。

不说的话，用户会以为收进去模型就查得到，然后因为查不到而认定资料库坏了。

## 四、Claude 那套 artifact 是另一个概念

一等对象、有版本、可回滚、可选择分享哪一版 —— 那是「反复改的交付物」，不是
「随时能取的参考材料」。要做也是**单独做**，别混进资料库：

* 资料库的条目是**不可变的内容**（内容寻址，`UNIQUE (blob_hash)`），
  artifact 的核心恰恰是**可变 + 有历史**
* 资料库按需被 `library_search` 检索，artifact 是用户直接打开来编辑的

混在一张表里的下场是 `blob_hash` 唯一约束与「同一份 artifact 的第三版」直接冲突。

## 五、三条都做完了（2026-09-02）

1. **上传/粘贴的附件自动收进资料库** —— 在**服务端** `POST /episodes` 之后
   （`episodes::collect_attachments`）。放客户端的话，从 CLI 发一个带附件的
   消息就不会进资料库，而 CLI 与 Flutter 走完全相同的 HTTP 协议。
   谁放进来的由 role 决定：user 那一轮记 uploaded，assistant 那一轮记
   generated。导入（`write_one`）**不自动收** —— 导一份 ChatGPT 存档会把
   几年的一次性截图一次灌进来。
2. **agent 交付的产物** —— 新工具 `deliver_file`：读工作区里的文件、上传成
   blob、挂成本轮 assistant 消息的附件。挂成附件之后剩下的路一条都不用新写
   （渲染、下载、跨设备同步），进资料库走的正是第 1 条那一步。判据是
   「有没有一个交给你的动作」，不是「落哪个盘」。
3. **配额 + 按大小清** —— `CORTEX_LIBRARY_QUOTA_BYTES`（默认 20 GB，
   0 = 不限），在唯一那个记录点 `library::insert_item` 上拦；
   `GET /library` 跟着列表回占用；资料库那一屏的副标题写
   「N 项 · 已用 X / Y」，右上角一个「按大小排」。

⚠️ **这三条是一个整体。** 第 3 条不做的话，前两条就是「无限长」——
而「不判断值不值得收」那个决定，正是以「膨胀有办法管」为前提才成立的。

顺带合掉了一个隐患：`library_items` 的 INSERT 此前有两份（HTTP 的 `add`
一份、画完图一份），`chunk_state` 的判据因此在两处各判一次。现在只有
`insert_item` 一句，三条路都打它。

## 六、还没做的

* **单份上限与总配额是两回事**：`deliver_file` 卡在 24 MB，总量卡在 20 GB，
  中间没有「一份 5 GB 的东西该不该收」这一档。真撞上再说。
* **pdf / docx / xlsx 提不出正文**，收进来是 `unsupported`，
  `library_search` 找不到它们。要各自的提取器。
* **配额是每租户一个数**，不分文件夹、不分来源。
* **满了之后是硬拒**，没有「自动清最旧的」。自动清会删掉用户以为还在的
  东西，而那比收不进去更糟 —— 收不进去至少日志里有一行。
* **`deliver_file` 的执行体没有端到端测试**（读文件 → 上传 → 挂附件），
  那要一个真的服务端。四道拦截与能力装配有测试，中间那段没有。
